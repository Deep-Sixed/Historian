### Assistant

That link is for **HashiCorp Vault**, now part of IBM/HashiCorp. Vault is a **machine/runtime secrets platform**: it stores secrets, issues short-lived credentials, rotates keys, brokers identity-based access, and can provide “encryption as a service” for apps and agents. HashiCorp’s page specifically markets it as protecting data in transit/at rest and reducing secret sprawl with short-lived, just-in-time credentials for developers, CI/CD, and AI agents. citeturn686706search0

## Passbolt vs Vault for Nexus

| Tool | Best for | Nexus role |
|---|---|---|
| **Passbolt** | Human-managed passwords, admin credentials, recovery kits, shared team secrets | Keep using it as the **operator vault** |
| **Vault** | Runtime secrets, dynamic DB credentials, app/agent tokens, leases, auto-rotation, encryption APIs | Potential future **machine secrets broker** |
| **Agent 9 Datacore** | Durable metadata/memory/events, not secret storage | Should store references/status only, **not secrets** |

## Does Vault apply to Nexus?

**Yes, but not as a replacement for Passbolt.**

For Nexus, Vault would make sense if you want:

- Short-lived Postgres credentials for Command Center services
- Agent-specific tokens that expire automatically
- Dynamic secrets for Agent 6/7 mail ingestion workers
- Runtime secret leases instead of long-lived `.env` values
- Central policy: “Agent 6 can read Gmail intake token, but cannot read DB admin password”
- Encryption-as-a-service for sensitive payloads without putting raw keys in app code

Vault’s GitHub description also highlights leasing/renewal and encrypt/decrypt APIs without the application managing encryption itself, which lines up with Nexus’s agent-boundary model. citeturn686706search6

## Important catch

Vault is **not fully open source anymore** under the old meaning. HashiCorp moved products including Vault to the **Business Source License 1.1**, which allows copying/modification/redistribution and non-production use, but with production/commercial restrictions depending on use case. citeturn686706search1turn686706search4

Also, IBM completed its acquisition of HashiCorp on **February 27, 2025**, so this is now part of IBM’s HashiCorp portfolio. citeturn204406search0turn204406search1

## My recommendation for Nexus

**Do not replace Passbolt right now.**

Use this progression:

1. **Current state:** Passbolt remains source for human/operator secrets.
2. **Near-term:** Keep `scripts/load-secrets-from-passbolt.sh` as the stable bootstrap path.
3. **Later:** Add Vault only when Nexus needs runtime leasing, dynamic credentials, or per-agent secret policies.
4. **Agent 9 rule:** Agent 9 records that a secret exists, what service depends on it, last validation status, and rotation metadata — **never the secret value**.

Best Nexus architecture would be:

```text
Passbolt
  -> human/operator credential vault

Vault
  -> runtime machine/agent secret broker

Agent 9 Datacore
  -> metadata, dependency graph, rotation status, health evidence

Command Center
  -> shows secret health, never secret values
```

So: **Vault fits Nexus, but as Phase 2/3 secrets infrastructure — not something to jam in before Command Center stability is locked.**
