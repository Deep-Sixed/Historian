# OpenRouter AgentCore Overview
### User

OpenRouter/ is the actual substance of the ContextForge-wired side — a whole AgentCore inference-dispatch subsystem, not just LiteLLM config. Breaking down what's actually in it, from what I found earlier this session:

agentcore/ — the real application. A FastAPI service (main.py, title "ContextForge LiteLLM Dispatch") with its own routing.py, dispatch.py, registry.py, probes.py, pull_rendezvous.py, db.py. This is what gets built into its own Docker image (nexus-agentcore:local) in the reference compose file — genuine application code, not just config.

agentcore_mcp/ — a control_plane/ client/server pair, exposing that dispatch service's control surface over MCP.

migrations/ — 4 raw SQL files (001_agentcore_schema.sql through 004_pull_rendezvous_v2.sql) plus a verification shell script — this thing has its own Postgres schema, separate from both ContextForge's DB and litellm-local's DB.

registry/ — YAML files (agent_nodes.yaml, inference_profiles.yaml) declaring which external agents can connect and what inference profiles they get routed to.

litellm-config/ — the actual LiteLLM-facing pieces:

consumers/ — per-agent connection docs + connect scripts for ~15 different clients (Cursor, Codex, Claude Code, Hermes, pi_agent, opencode, continue_vscode, ensemble, etc.)
litellm_plugins/ — custom LiteLLM callback plugins: hindsight_memory (ties into the Hindsight memory system we discussed earlier), custom_logger, combine_system_messages, remove_name
scripts/ — key-generation and KeePassXC-batch-write helpers
deployment/ — compose.reference.yml (the template I checked — nothing from it currently running) and an nginx bridge config for exposing the host-network LiteLLM proxy to Docker-bridge containers.

tests/ — a real pytest suite for the AgentCore dispatch/routing/probes logic (7 test files).

Dockerfile — builds the AgentCore image.

So in one line: OpenRouter/ is a self-contained inference-dispatch control plane (own DB schema, own FastAPI app, own MCP control surface) that sits between many different agent clients and LiteLLM/ContextForge — not a config folder, an actual unbuilt service.

### Assistant

**OpenRouter is an agent traffic controller.**

It sits between tools like **Codex, Claude Code, Cursor, and Hermes** and the actual AI models served through **LiteLLM**.

It:

- Decides which model or inference profile each agent should use.
- Dispatches requests to LiteLLM.
- Tracks agents, routes, probes, and connection state in its own database.
- Exposes its controls through an MCP server.
- Adds custom LiteLLM behavior, logging, and Hindsight memory integration.

So it is **not OpenRouter.ai and not merely LiteLLM configuration**. It is a separate **AgentCore routing and control-plane application** that was designed but is currently **not deployed or running**.

### Assistant

You mean **MPLS** — *Multiprotocol Label Switching*.

AgentCore was your **AI-routing equivalent of MPLS/SD-WAN**:

- Agent identity/profile acted like a routing label.
- AgentCore selected the permitted inference route.
- LiteLLM forwarded the request to the chosen model/provider.
- Health probes and fallback rules changed the route when a backend failed.

So it was not literally an MPLS network, but you were applying the same idea to **AI inference traffic**.

**MLP** means *multilayer perceptron*, a type of neural network, which is unrelated here.

### User

Multiprotocol Label Switching (MPLS) is a private, high-performance wide area networking (WAN) technology that directs data packets along predetermined paths using short "labels" rather than long network addresses. It speeds up data delivery and ensures high reliability for business-critical applications.

### Assistant

That is the networking concept you were borrowing from.

For your AgentCore/OpenRouter system, the analogy was:

| MPLS networking | AgentCore inference routing |
|---|---|
| Packet receives a label | Agent request receives an identity/profile |
| Label selects a predefined path | Profile selects a model/provider route |
| Router forwards without recalculating everything | AgentCore dispatches through LiteLLM using stored policy |
| Traffic classes receive different priority | Different agents receive different models, limits, and fallbacks |
| Failed links trigger alternate paths | Failed providers or models trigger fallback routes |

So AgentCore was effectively an **MPLS-inspired control plane for AI inference traffic**.

The label was not attached to a network packet. It was represented by things such as:

- agent identity
- inference profile
- permitted providers
- model priority
- fallback chain
- routing policy

That explains the separate registry, probes, database schema, dispatch service, and MCP control plane. It was intended to provide **deterministic, policy-controlled routing**, rather than allowing every agent to call any model directly.
