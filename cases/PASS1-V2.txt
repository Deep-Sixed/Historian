| Stage | RAG Type | Status | Purpose |

### In chronological order

2. **LightRAG**

3. **Hindsight Memory**

     - task history,
     - artifacts,
     - decisions,
     - previous outcomes.
   - Became the primary memory substrate.

4. **Datacore (Hermes)**

     - task memory,
     - cross-session continuity.

```text
Classic Chunk RAG
        ↓
LightRAG (GraphRAG prototype)
        ↓
Hindsight Memory (working GraphRAG)

Datacore persistent memory
```

Conceptually, the stack had shifted from:

```text
RAG over documents
```

to

```text
RAG over knowledge graphs
```

and finally toward

```text
RAG over agent experiences + persistent memory
```

which is closer to an episodic memory architecture than a conventional vector-database RAG system.

## What it is

It functions as an **Agent Control Plane (ACP)** built on top of LiteLLM’s routing layer.

Where LiteLLM itself is mainly:
- Multi-provider LLM router (OpenAI, Anthropic, etc.)
- API normalization layer
- Fallback + load balancing gateway

This project adds a higher layer focused on:

- Agent identity
- Policy enforcement
- Tool / MCP governance
- Execution routing for agent workflows
- Auditability across tool calls and model calls

## Core idea

It separates concerns:

- **LiteLLM = data plane**
  - Sends prompts to models
  - Handles routing, retries, fallbacks, cost tracking

- **Agent Control Plane = control layer**
  - Decides *whether an agent is allowed to act*
  - Governs tool access (GitHub, DBs, MCP servers)
  - Enforces budgets, policies, approvals
  - Tracks full execution chains across agents

## What this repo is trying to solve

It targets a gap in most agent stacks:

- LLM gateways handle **model routing**
- Agent frameworks handle **behavior (LangGraph, CrewAI, etc.)**
- But nothing consistently handles:
  - Cross-agent authorization
  - Tool-level permissions
  - End-to-end traceability of multi-step agent runs

This project positions itself as that missing layer.

## Typical architecture implied

```
User / Agent Framework
        ↓
Agent Control Plane (this repo)
  - policy engine
  - identity + budgets
  - tool permissions
        ↓
LiteLLM Gateway
  - model routing
  - provider abstraction
        ↓
LLMs + Tools (MCP, APIs, GitHub, etc.)
```

## Key components (conceptually)

Even if implementation details evolve, ACP systems like this usually include:

- **Agent registry**
  - defines what agents exist and their permissions

- **Policy engine**
  - “this agent can call GitHub.read but not GitHub.write”

- **Execution ledger**
  - logs every tool call + model call

- **Budget enforcement**
  - token / cost limits per agent or workflow

- **Tool gateway integration**
  - often MCP-based or HTTP tool proxies

## Why it exists now

This is part of a broader shift:

- LLM apps are becoming **multi-agent systems**
- Tool calls are becoming **production-critical actions**
- Simple API gateways (like LiteLLM alone) don’t handle:
  - identity propagation
  - tool authorization chains
  - audit-grade traceability

So this repo is essentially an attempt to turn:
> “LLM routing infrastructure”  
into  
> “agent operating system control layer”

## Relationship to other similar systems

It overlaps conceptually with:

- Agent orchestration systems (LangGraph-style)
- Kubernetes-style control planes for workloads
- IAM systems (but for agents instead of users)
- MCP gateway/security layers

But its framing is specifically:
> “control plane for agentic workloads using LiteLLM as the execution layer”
